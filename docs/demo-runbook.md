## Live Workflow

### 1. Open The Intake

In a new local project session with the MOSAIC Orchestrator selected, enter:

```text
menu
```

The opening menu must appear immediately, without contract reads, repository searches, commands
or an extended reasoning delay. Select:

```text
1
```

The agent must immediately ask for the business problem. Then enter this fictional end-user request:

```text
I run Employee Services at Contoso Public Services. Our field staff keep getting travel claims rejected because they follow old mileage and hotel guidance. The rules are spread across intranet pages, PDFs and saved email replies. My team keeps answering the same questions, and Finance has to correct claims after people have already spent the money.

I want employees to be able to ask "Can I claim mileage for this trip?" or "Who needs to approve an overnight stay?" and get an answer linked to the current policy. Anything that needs an exception should go to the right person in Finance, not receive a guessed answer.

Help me work out how to fix this before I take a proposal to our Finance and IT leads. Would better search be enough, or would an assistant help? I need to understand the options, the likely effort and running costs, who would keep the information current, and how we would tell whether rejected claims and repeat questions are actually going down.
```

Continue with one descriptive question at a time. Every interview turn must remain conversation-only, not only the menu and first question. The first business-problem question contains only business-need choices. Starting with the next question, options begin with **End intake and generate report**, followed by relevant business choices and **Something else**; free text remains available. Do not display Continue, Pause or Resume menus, a standalone generate banner, or capture/debug narration. Do not give the business user a fixture, evidence-ID list, specialist script or test command. Defer policy, evidence and generation-contract reads until the user asks to generate; save the transcript in one batch after plan approval, before analysis. If the agent delays any question for file writes, capture commands or setup, skips intake or runs the example, stop the rehearsal and repair the entry instructions before recording.

### 2. Approve The Bounded Plan

Answer the relevant questions using these fictional scenario facts, in ordinary language:

```text
Keep this to travel claims for 250 field staff. I need a proposal by 15 October, not a deployment. There is up to $30,000 for initial work. Finance owns the policy, and the current documents are in SharePoint. I don't have a reliable baseline for rejected claims or repeat questions yet. My biggest concern is giving someone the wrong answer.
```

When ready, enter:

```text
That's enough. Use what I've given you and generate the documents.
```

If the bounded plan has not yet been approved, the agent must disclose the four allowed synthetic sources, the separately authenticated Copilot CLI model connection, its configured credit cap/deadline, the local transcript boundary, 23 outputs and the human-review stop. Notifications are disabled, the transcript is excluded from the model prompt, and paid inference is never retried automatically. The year of the supplied date, detailed costs and other missing business inputs remain unknown. The synthetic sources establish control principles, not proof of these conversation statements. Approve only a plan without customer connectors, external writes, implementation, deployment or automated customer decisions:

```text
Yes, go ahead.
```

Switch from Plan to Interactive for the approved generation step when required by the App. Do not restart optional questions or type a developer tool script.

### 3. Show Connected Evidence

Show the actual approved acquisition for this run, or label archived Local MCP captures explicitly as earlier evidence. Do not splice a prior tool result into a new sequence as though it belongs to the current request. The four allowed sources and their original bytes remain unchanged.

### 4. Prepare And Open The Report

The configured engine performs the approved bounded analysis and report assembly synchronously. A brief **Preparing your documents...** status is sufficient; do not show internal commands, job identifiers, debug output or invented progress. Remain with the same run until it completes or reports an actionable failure. Do not poll, launch a second generation or wait for a Windows notification.

The completed handoff leads with **Your intake report is ready**, the exact report link and **Open documents in browser**. Open only on the user's selection. Show the actual report, not its diagnostic status page. A successful browser launch request is not proof of customer review or approval.

The package contains 23 artifacts: ten HTML pages, nine Markdown reports and four JSON records, including the transcript. This is one separately authenticated model call plus local validation, not native App multi-agent proof. The PC and generation process must remain on. Complete development tests before the end-user rehearsal, not while the participant waits for documents.

For operator verification, open the separate **Processing cost & pipeline trace** report. Inspect stage timings, recorded usage and the explicit App-coverage gap. A credit cap is not consumption, a credit-equivalent dollar value is not an invoice, and an unsuccessful call must not be assumed free. Do not substitute backend-only timings or tokens for the complete App experience. Keep diagnostic tables outside the customer assessment and do not wait for another AI-generated summary of the trace.

### 5. Inspect Decision Artifacts

Show, in this order:

1. overview, under-title dates, unverified submitter, business need and two blocked customer decisions
2. scope, $30,000 ceiling, partial proposal date and unknown baseline, visibly attributed as assumptions
3. intake transcript, including capture-session start/end, original answers, corrections and generation-only approval
4. three contrasting options and conditional recommendation using common criteria
5. risk/unknown counts, evidence map, section information controls and acronym explanations
6. discussion agenda and 30-minute talk track

Do not read documents line by line. Use the generated HTML report as the fast visual index.

### 6. Preserve Human Authority

End on the human-review report: architecture selection pending, exact-revision design approval blocked pending selection, and release unauthorized. No qualified reviewer action is invented. If a real separately authorized review or correction occurs, retain and show that evidence; do not script one merely for the recording. A pull request is review evidence, not the customer's decision system. Do not merge, release or submit the contest form during capture.
