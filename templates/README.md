# Report Templates And Contracts

MOSAIC's reporting layer is designed to be highly customizable for each isolated customer: branding, terminology, required document profiles, section wording, reviewer roles, evidence policies, control mappings and approval language can vary while the governed process remains stable. These templates define the minimum customer-adaptable document surfaces. Double-braced names are structured fields supplied by an approved renderer. Rewording headings is allowed; removing evidence, maturity, unknown, risk, decision, or approval sections is not.

The [Markdown renderer](../src/mosaic/render.py) composes canonical documents from the validated workflow package. The Markdown `.tpl` files below remain adaptation contracts, not executable inputs. Policy-required reviewer roles are applied from customer configuration. The contest reference supports maintainable template adaptation and document-profile compatibility checks; arbitrary runtime template selection, branding controls and zero-code terminology mapping remain product-extension work rather than proven capability.

The [HTML renderer](../src/mosaic/reports.py) executes [report.html.j2](report.html.j2) for the overview and nine report pages. [report.css](report.css), [report.js](report.js), [report-glossary.json](report-glossary.json) and [report-icons.json](report-icons.json) supply shared theme, navigation, explanations and Lucide assets. They are embedded in each file so viewing requires neither a network nor a server. The sidebar presents all document links directly, without a search or filter field. [job.html.j2](job.html.j2) is the local diagnostic status template, not the completed-document handoff. Jinja autoescaping, raw-HTML-disabled Markdown parsing and a restricted local-link policy protect report content; no raw user content becomes executable markup.

The complete package has ten HTML pages, nine Markdown reports and four JSON records. The [transcript renderer](../src/mosaic/transcript.py) produces the transcript directly from validated captured history; no adaptation template or model reconstructs it. Preserve exact text, whitespace, fidelity, gaps, controls and the separate session-capture start/end times. Older reference inputs without conversation history must remain `not_recorded`.

The separate [processing template](processing.html.j2) is operator diagnostics, not a customer assessment page. It displays recorded execution timing, usage coverage, credit-equivalent value and the full observable pipeline trace. It has no scripts or remote resources; active jobs refresh the local view. Missing measurements must remain visible, the credit cap must never appear as consumption, and legacy request multipliers must not be converted to AI credits or dollars. The backend renderer supplies only allowlisted metadata, never prompts, business answers or model reasoning. `npm run test:reports` also checks this page when it is present beside a job's customer report directory.

Every report is titled for the operator's use case and written for a human technical specialist. The overview begins with the original request, executive summary, affected users, stakeholders, scope, current environment, requirements, proposed measures, unknowns, options and next decisions. Supporting reports provide the detailed evidence, architecture, security, interfaces, risks and review records needed to challenge the assessment. Section help explains material limits without repeating generic process language.

The request schema is shared by conversational and prepared-input validation. Stakeholders may be role-name strings or records with `role` and `authority`, including mixed lists. Role names display an explicit unknown authority; an omitted or empty list remains visibly unknown, never invented. Preserve the original records in the structured package. Test each supported shape through full report rendering and the job publication path, not only input validation. Multiline business prose is compared as visible text in browser checks; transcript checks still preserve exact whitespace and wording.

The reports are working documents: discovery follow-up, source verification, option-selection prerequisites, requirement-to-plan traceability, blocker disposition and separate customer decision records. The engagement package provides participant preparation, a time-boxed agenda with expected working outputs, evidence questions, decision boundaries, meeting exit criteria and facilitator readback. Proposed actions, owners and dates must never be presented as assignments or agreements already made.

The transcript uses one session summary and an ordered conversation with the supplied end-user name or John Doe and MOSAIC. Show reply links only for recorded relationships, fidelity warnings only for summarized capture and dates only when captured. Offered choices are expandable; recorded answers and corrections remain visible. Do not add empty-field placeholders, repeat verbatim labels or change the original payload to improve its presentation.

The report identity is **{initiative title} - Initial Technical Intake Assessment**. The visual system is consistent across the package, while MOSAIC appears only as preparation provenance rather than the subject of the customer report. The overview places report-generation and intake-received dates beneath its title, followed by the unverified submitter and preparation provenance. The John Doe fallback is a labeled placeholder, not authenticated authorship. All pages in a render share `package.reportMetadata.generatedAt`; do not substitute the deterministic workflow timestamp or invent missing session dates.

Visuals count actual records and show qualitative comparisons, not invented fit scores, probability, completion percentages or measured benefits. Bar charts show recorded source dependencies, option conditions, risk severity, shared blockers and captured entry types. Heatmaps show requirement/source, requirement/plan and blocker/plan references. The meeting allocation is proportional to its recorded minutes. Include visible values and the basis and limits of each visual; omit unsupported trends and empty conversation analytics. Multiple source references are not independent confirmations, and plan references are not completed work. Wide tables remain locally scrollable and keyboard accessible.

Controls explain sections and terms on hover, focus and touch. Unknown acronyms are explicitly flagged rather than given fabricated definitions. Preserve the [icon license](lucide-LICENSE) with redistributed icons.

Validate changes with the Python report/job tests and `npm run test:reports -- <generated-report-directory>`. The Playwright validator checks every report at four widths, offline links, keyboard/touch help, mobile navigation, themes and automated WCAG A/AA rules. It compares chart values and heatmap cells to the structured records and verifies report definitions, section-specific help and exact transcript text, sequence, participants and reply links. Exercise both an uncaptured reference and a populated conversation, including summarized capture. Screenshots still require visual inspection; passing automation is not accessibility certification.

Maintain JavaScript and CSS in readable source form using `npm run format`. Vendored icon data, original evidence and generated canonical output are formatter exclusions. Follow [CONTRIBUTING.md](../CONTRIBUTING.md) for attribution and regenerate only the canonical reference after approved template changes; preserve existing completed intake revisions.
